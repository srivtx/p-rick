Method

How p-rick decides what to research. The bar is deliberately high: the program hunts for software categories that do not exist, not projects that are merely unbuilt. This page states the bar, the exclusions, the grading, and the discipline every paper passes through before it is called research.

The bar — four tests, all mandatory

A direction becomes a paper only if it passes all four tests. The problem must be real: a failure mode that recurs, hurts, and is documented in incidents, studies, or expensive behavior — not a hypothetical nobody has suffered. The audience must be large: millions of people or an entire profession, not a hobby community. The category must be empty: verified against the landscape before writing, with every adjacent incumbent named and its boundary stated — “no incumbent anywhere in the center” is a falsifiable claim, and one search can kill it. And the result must be specifiable: formalizable into a model, protocol, or architecture that a builder could implement and an evaluator could test — a feeling is not a deliverable.

The exclusions — what the program will never ship

The exclusions are as deliberate as the bar, and they are enforced as hard rules. No toy projects: nothing whose primary value is demonstration, novelty-of-implementation, or portfolio value. No deterministic wrappers: no test suites, verification gadgets, “verified wrapper” utilities, or deterministic-crypto proof-of-correctness artifacts whose only user is their own construction. No AI-obsolete software: nothing whose reason-to-exist disappears the moment a model can do it; the program prefers gaps the AI era makes larger. No CRUD, no chatbot shells, no dashboards-as-research. And no me-too products: if the category exists and is merely under-served, that is a product review, not a gap. The program publishes specifications for missing systems — not apps, not demos, not libraries wrapping an afternoon's insight.

The pipeline — survey, claim, grade, specify, red-team

Every paper travels the same route. Survey before writing: multi-agent landscape scans that name the incumbents, the near-misses, and the dead research lines; directions that die in survey die quietly, with their notes kept. Falsifiable gap claims: “nothing exists that does X” is written so that one search can refute it — and claims are scoped to survive the search (“component PARTIAL, composition STRONG” is an honest verdict; the program uses it). Graded evidence: STRONG / PARTIAL / WEAK verdicts appear in the papers themselves, including where the strongest objections might kill the thesis. Specification over prototype theater: formal models, protocols, threat models, and evaluation designs — the artifacts a builder actually needs, before any code exists. Red-team pass: adversarial review challenges novelty claims, headline figures, formal properties, and cross-paper consistency; findings are fixed, not footnoted. And an essay with every paper, because research nobody reads is a diary.

Citation honesty

Papers are drafted with domain knowledge and marked citations, then pass through a live-source verification ledger before final release. References recorded from prior knowledge are flagged verification queued until the pass completes; the ledger travels with the sources, and corrections are applied to the papers rather than argued around. Where the program is confident, it says so; where it is provisional, it says that too.

Work tracking

The program logs itself: agents.md is the automatic session ledger — what was done, when, and by which agent. Research first, products later, in separate directories, only after the research freezes.
